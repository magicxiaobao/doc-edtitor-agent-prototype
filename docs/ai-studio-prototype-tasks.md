# Google AI Studio公文辅助协作原型任务提示词

版本 v0.1  日期 2026年10月7日

本任务包将核心产品流程拆成六批可运行的前端原型任务。基线为同目录的[需求文档](requirements-v0.1.md)。本轮用于验证界面、状态和交互；真实RAG、内网模型、后端权限及生产部署留待后续实现。

## 使用方法

1. 在Google AI Studio Build模式新建Web项目，复制“共用提示词”及“任务01”作为首次请求。平台若已导入本仓库并能读取docs，也可以指明读取本文件和执行指定任务。
2. 每次只执行一批。任务完成后先按该批验收路径操作，再同步到本仓库；后续任务在同一项目继续，不重新建一套应用。
3. 仓库已有docs是基线，保留这些文件。代码生成后可在Settings的GitHub页关联现有仓库，先核对仓库现有内容，再同步代码。不要仅因提示词中提供URL就认为AI Studio已经有仓库访问权限。
4. 每批以一次清楚的提交记录范围；可按阶段创建分支并合并，也可顺序提交到main。同步前先拉取最近变更；有冲突时核对文件，不用整仓覆盖。
5. 若AI Studio的当前账号不能关联该仓库，导出代码ZIP，再把代码提交到指定仓库。保留原有docs；不要把问题转成另一个仓库。
6. 评审时提供批次号、提交SHA及启动方法。若有可访问预览链接或关键页面截图，也一起提供；仓库代码可以支持结构评审，交互和视觉评审还需要实际运行页面。

Google官方说明Build模式支持自然语言生成Web应用、GitHub导入和双向同步；具体入口以账号当前界面为准。[官方文档](https://ai.google.dev/gemini-api/docs/aistudio-build-mode)

## 共用提示词

首次与任务01一起粘贴。后续在同一项目继续；新会话时重新提供共用提示词与已完成批次。

```text
你是负责实现产品原型的前端工程师和交互设计师。请制作“公文辅助协作”的可运行 Web 原型，优先服务单位内的主笔和审阅者，用于工作总结与汇报材料。当前任务是验证页面和交互，业务服务先使用可重复的模拟数据。

必须遵守以下共用要求。

1. 业务流程为：建任务 → 整理材料和事实 → 主笔确认事实 → 提取并确认单位文风 → 编辑并确认大纲 → 起草 → 审阅修改 → 定稿导出。主笔编辑正文，他人供稿或审阅。AI 给出建议，人决定采纳；关键阶段不能仅切换页面就视为确认。
2. 原型运行时不调用 Gemini、外部模型、网络搜索、真实 RAG、云数据库或外部账号系统。模拟 RAG 和生成服务，通过类型化接口隔离，未来可以替换为内网服务。使用虚构材料，不写入任何真实单位信息、内网地址或密钥。Google AI Studio 用来生成代码，与产品运行时的网络边界分开。
3. 若已有前端代码，沿用框架和组件；若从零开始，使用 React、TypeScript 和适合该环境的轻量构建方式，项目应支持本地安装、开发和构建。样式和图标打包到项目中，使用系统中文字体；不要添加运行时 CDN、外部字体、图片接口和遥测。不要搭建业务后端。
4. 使用统一类型和任务级状态。事实、证据、大纲、正文段落、意见和版本都要有稳定 ID，不能按数组位置关联。模拟服务、组件和状态管理分开。正文使用结构化段落，保留段落与事实的引用关系。
5. 只保存必要的演示状态到浏览器本地，包含版本号、迁移或重置策略。演示文件只持久化元数据及虚构片段，不把大文件序列化进 localStorage。刷新恢复当前任务；切换任务不能串数据。提供“重置演示数据”，执行前确认。
6. 使用中文桌面办公界面。以白色文稿、浅灰背景、深蓝主操作色、清晰表格和紧凑工具栏为主。正文区域最重要，避免营销首页和占据主屏的统计卡片。正文预览至少16px；表单和工具文本至少14px；状态同时有文字，不能只靠颜色。主工作区在1440px和1280px桌面宽度可用，1024px允许折叠辅助栏，窄屏改用抽屉或页签。
7. 一篇任务使用同一份数据，所有计数、侧栏、正文引用和按钮状态由数据计算。不要为每页写互不关联的展示数组。异步模拟支持加载、无结果、失败、取消和重试；失败不能删除已有成果，取消后迟到结果不能写回。
8. 产品界面使用“材料依据”“待补充”“修改建议”等业务语言。以简短“演示模式”标识说明数据为模拟；接口细节放到演示控制区和README，不放进主笔的正常流程。
9. 所有已交付功能的按钮必须真正改变状态、打开相关内容或执行对应操作。尚未到本批实现的功能明确禁用并说明原因。不能用“成功”toast代替实际保存、修改、下载或确认。
10. 只完成我本次指定的任务，不提前实现后续批次。保留已完成交互及仓库docs，不能覆盖或删除规划文档。完成后停止，汇报变更文件、运行方法、验收步骤、已核验结果和未完成项。
11. 每批更新docs/prototype-progress.md，包含批次、实现范围、人工验收路径、构建结果、未完成项和建议提交信息。只有确实运行过的检查才能写为通过；角色切换是界面演示，不代表服务端权限已验证。
12. 仓库目标是 magicxiaobao/doc-edtitor-agent-prototype。平台已连接仓库时，在当前任务完成并核验后同步代码；未连接时说明需要的导出或同步操作，不声称已经提交。不能仅凭提示词假装有GitHub权限。
```

## 任务01 工作台与任务工作区

```text
请遵守共用要求，只实现任务01“工作台与任务工作区”，完成后停止。

目标：让主笔能建立写作任务并进入一个完整、可继续扩展的工作区。本批不实现事实分析和正文生成。

页面和布局：
- 任务工作台：任务名称、文种、统计期间、主笔、阶段、更新时间；支持搜索和按阶段筛选。新建任务为主操作，使用列表或表格，避免大型统计仪表盘。
- 新建任务：主题、工作总结或汇报、用途、受众、统计起止日期、目标字数、必须覆盖内容、截止时间。必填校验和期间校验真实生效。
- 任务工作区：顶部显示任务名称、期间、当前阶段和保存状态；主导航包含任务要求、材料与事实、文风与大纲、正文、审阅、版本与导出。步骤能浏览，但未满足条件时关键操作禁用并解释。
- 当前可编辑区域为任务要求；后续页面显示该批未实现提示及合理布局，不能展示假完成结果。

统一演示场景：
先建立“某单位2026年前三季度工作总结”，统计期间2026-01-01至2026-09-30，面向单位负责人，目标3000字。另提供一个空白新任务和一个已有草稿的预置任务；预置任务必须有对应合法的事实、大纲和版本状态，不能靠阶段标签伪造流程完成。
使用虚构人物“主笔甲”“审阅乙”“供稿丙”。后续批次继续使用这份场景。

工程约定：
定义Task、SourceDocument、EvidenceSnippet、Fact、StyleProfile、Outline、DraftVersion、ReviewComment及AgentRun等初始类型。持久化按任务隔离、带schemaVersion。可用等价结构，不要求此时实现所有对象行为。
提供统一按钮、表单、状态标签、空状态、抽屉和确认框组件。路由或页面状态需支持返回和刷新恢复；不要为每次新任务生成另一套组件。

验收：
1. 新建任务后列表出现真实新记录，打开后能修改要求，刷新仍保留。
2. 起止日期颠倒或主题为空不能创建，并有具体错误提示。
3. 搜索和筛选能影响列表；无命中显示空状态。
4. 两个任务之间切换不共享未保存输入；保存状态明确。
5. 未实现的起草按钮不能直接跳到假定稿。
更新README及docs/prototype-progress.md，记录运行方法和任务01验收路径。建议提交信息：feat: add task workspace prototype。
```

## 任务02 材料与事实确认

```text
在现有项目上只实现任务02“材料与事实确认”，遵守共用要求，保留任务01。

目标：展示材料如何变成可确认的事实。对应需求FR02至FR05，重点实现原文查看、口径冲突和资料缺口。

材料区：
支持添加演示材料、上传文件元数据及粘贴文本。记录材料名称、来源、期间、用途和解析状态。本批只承诺解析TXT及粘贴文本；DOCX和PDF可选择并记录元数据，但明确“待接入解析”，不能凭扩展名声称已经读取内容。提供内置已解析虚构材料供完整演示。
材料用途区分本期事实、历史背景、文风参考和检索线索。列表可搜索、筛选、排除使用。点击片段打开原文查看抽屉，突出对应片段及其文档、期间、页码或段落位置。

模拟RAG：
创建mockRagService，支持正常命中、只有生成答案、无结果、超时和无权限五种返回场景。前台展示检索问题和结果；演示控制区用于切换返回场景。
只有答案的结果显示“检索线索，待提供原文”，不得产生虚构页码和已确认事实。
原文展示来自本地虚构片段，不去打开真实网站。

事实清单：
包含指标或事实、期间、数值、单位、统计口径、来源和状态；支持确认、编辑、排除和查看依据。编辑事实注明主笔补充，不悄悄修改原文。
至少提供正常事实、重复材料、120与128的冲突、2025年的旧数据、没有原文的答案以及缺失满意度指标。
冲突处理面板并列展示候选值与原文。主笔可选择一项并填写理由，或排除该事实继续；系统不能自动取更大值、最新返回值或平均值。
缺口列出具体待补事项。所有状态数量由事实清单计算。

流程规则：
“确认本次事实清单”只确认已选择且依据满足条件的事实。存在被纳入本次写作的关键冲突或无依据事实时，提示先处理；主笔可以明确排除后继续。确认动作生成快照；后续修改事实使相关确认失效并提示复核。
原始材料、事实确认和引用关系分开保存。

验收：
1. 从事实能打开正确原文及定位；历史文风材料不会成为本期已确认事实。
2. 120与128必须人工处理，处理后任务内的计数同步更新，刷新结果保留。
3. 仅答案的RAG结果不显示伪造出处，不自动确认。
4. 无结果、超时和无权限有不同反馈；重试不重复追加同一条证据。
5. 明确排除冲突后可继续；未经处理不能越过事实确认。
更新进度文件并提供操作路径。建议提交信息：feat: add evidence and fact confirmation flow。
```

## 任务03 单位文风与大纲确认

```text
在已有项目上只实现任务03“单位文风与大纲确认”，遵守共用要求，保留前两批。对应FR06和FR07。

单位文风：
展示本单位历史定稿列表，允许主笔勾选参考样稿。模拟提取标题组织、章节顺序、段落表达、正式程度等规则，规则附对应样稿片段。
```

## 任务04 正文编辑与依据查看

```text
在现有项目上只实现任务04“正文编辑与依据查看”，遵守共用要求，保留前三批。对应FR08、FR09及FR13的基础版本能力。

工作区：
以正文为视觉中心，左侧为可折叠章节导航，右侧为可切换的材料依据与修改建议。正文像可编辑文稿，标题和段落层级清楚，不设计成聊天消息流。
1440px可同时看正文和依据；1280px保证正文宽度，必要时折叠章节栏；1024px用抽屉查看依据。
允许主笔按段落编辑和保存，维持稳定Block ID及事实引用。编辑器可使用现有富文本组件或结构化段落编辑，避免构建复杂分页排版引擎。

模拟起草：
必须先确认事实、文风和大纲。mockDraftService依据当前选定事实和大纲生成确定性正文，数据值来自状态，不能把120或128写死到生成模板。
显示当前阶段，可取消、重试；完成前不替换现有正文。再次生成先提供新候选稿，主笔决定替换或保留。
正文中的数字、期间和主体可打开关联依据。主笔手工新增无依据数字时提示待核对，不生成虚构来源。

局部修改：
选择段落，提供压缩、扩展、正式表达和突出重点等操作。模拟服务给出前后对比及“涉及事实变化”的说明，操作为采纳、拒绝、重新生成。只有采纳才更新正文。
演示压缩后仍保留16场、800人次及对应期间；不能把人次改成人数。缺少满意度数据时继续标注待补或省略。
建议关联基准版本；生成建议后主笔又编辑同段时，采纳需提示冲突，不能直接覆盖。

基础版本：
手动保存版本并列出时间、创建者、摘要。对比至少到段落，恢复历史稿产生新版本，保留历史记录。
事实变动时标出依赖该事实的正文段落；没有事实关联的普通过渡语不应全部误标。

验收：
1. 修改冲突选择后重新起草，正文采用当前确认值；未选择的冲突值不进入正文。
2. 取消生成不产生迟到覆盖，刷新恢复已保存正文。
3. 从正文查看依据能定位正确事实和原文。
4. 采纳前原文不变，拒绝不写正文；基准已变化时能看到冲突。
5. 恢复旧稿后旧版本和新版本都存在。
更新进度文件和运行记录。建议提交信息：feat: add drafting workspace and revision preview。
```

## 每批通用验收

- 当前批的主操作有实际行为，数据更新后列表、正文、侧栏和计数一致。
- 同一任务刷新后恢复；另一个任务的数据不被覆盖。
- 用户能看见关键事实的来源、确认状态和统计期间。
- 模拟RAG只有答案时保留“待提供原文”，生成不会把缺失数据补成事实。
- AI生成与修改建议只有经过对应人工操作才推进流程或写入正文。
- 取消、失败、版本变化不会覆盖最近保存的成果。
- 使用系统字体及项目内资源；产品运行时不要求访问外部API。
- 实际运行构建并记录结果；未运行的视觉、权限和Word兼容检查列为待核验。
